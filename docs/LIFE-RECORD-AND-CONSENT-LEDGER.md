# Tupua Life Record and Consent Ledger
## Development specification — private-first, evidence-aware

**Status:** Design specification only. Not a deployed or activated logging service.  
**Target:** Tupua-App development branch.  
**Security posture:** No personal testimony, private contact details, medical information, or allegations belong in this public repository.

## 1. Purpose

Provide a user-controlled record of personal experiences, creative work, project decisions, testimony, and system changes. The ledger supports continuity, provenance, review, and lawful accountability without presenting unverified claims as established facts.

## 2. Record model

Each entry should contain:
- \`record_id\`: locally generated unique identifier.
- \`recorded_at_utc\`: ISO 8601 UTC timestamp generated by the recording device or trusted server.
- \`event_time\`: optional time the described event allegedly occurred; keep distinct from recording time.
- \`author\`: account or local profile that entered the record.
- \`entry_type\`: journal, testimony, creative work, project change, source, correction, or export.
- \`statement\`: the author's words, preserved without silently rewriting.
- \`evidence_refs\`: optional references to files or sources, with hashes where feasible.
- \`epistemic_status\`: firsthand account, independently corroborated, documented source, interpretation, hypothesis, belief, metaphor, or fiction.
- \`confidence_note\`: optional explanation; never fabricate a numeric confidence score.
- \`privacy_level\`: private, selected recipients, or public.
- \`sharing_consent\`: explicit recipient and scope approvals, with timestamp and revocation state.
- \`revision_of\`: prior record identifier for corrections; original entries remain auditable.

## 3. Evidence and fairness safeguards

- Distinguish when an entry was recorded from when the event is said to have happened.
- Attribute contact or recognition claims to the person making the report unless independently verified.
- Do not infer that a named person or institution participated in wrongdoing from a mention, feeling, coincidence, or unverified communication.
- Allegations must identify the specific conduct, approximate date, available evidence, and what remains unknown.
- Preserve material that supports, contradicts, or is neutral toward an allegation.
- Corrections append a new linked record; never silently overwrite the original.
- Use neutral language and allow a response or correction where appropriate.
- Refer potential legal violations to qualified legal counsel or the appropriate independent authority; the ledger itself makes no legal finding.

## 4. Privacy, security, and sharing

- Default all personal entries to **private**.
- Do not auto-send, publish, email, or disclose entries to family, friends, public figures, companies, government agencies, courts, or other recipients.
- Sharing requires a preview and a separate affirmative approval for each recipient or clearly defined recipient group.
- Show exactly which fields and attachments will be shared.
- Allow the user to cancel or revoke future access where technically possible; explain that copies already received cannot be recalled.
- Encrypt private records in transit and at rest; do not treat browser localStorage as secure storage for sensitive records.
- Keep secrets, passwords, access tokens, medical records, and unnecessary third-party personal data out of logs.
- Use access controls, secure backups, retention controls, and an auditable export history.
- Never place real personal records in this public source repository. Production storage must be private and separately secured.

## 5. Timestamp and integrity model

- Store timestamps in UTC using ISO 8601; display local time only as a presentation conversion.
- Keep device time as a user/device assertion unless corroborated by a trusted timestamp service.
- Optionally hash exported record bundles and preserve the manifest; a hash can show whether a file changed, but does not prove that its contents are true or that its timestamp is accurate.
- Record application version, schema version, and export time.
- Do not claim an immutable or tamper-proof record unless the deployed infrastructure has been independently tested to support that claim.

## 6. Review and export workflow

1. Create a private draft.
2. Show the timestamp, statement, attachments, and epistemic status.
3. Let the user correct or annotate the draft before saving.
4. Save privately and append an audit event.
5. For an export, preview the exact contents and recipient.
6. Require a separate approval before any external transmission.
7. Record the export result without claiming delivery unless the sending service confirms it.

## 7. Acceptance criteria

- Personal records are private by default.
- No automatic external disclosure exists.
- Recording time and event time are separate fields.
- User statements remain distinguishable from corroborated facts and interpretations.
- Corrections preserve prior versions and provenance.
- Exports show recipient, contents, and consent.
- Sensitive records are not stored in this public repository or unencrypted browser storage.
- Tests cover access control, consent, correction history, timestamp formatting, and export boundaries.

## 8. Implementation boundary

This file is a design specification committed to a development branch. It does not install or activate a runtime service, create personal records, connect external institutions, contact named individuals, or modify Base44, production databases, email, messaging, or cloud infrastructure. Implementation requires a private storage design, threat model, code changes, tests, and a separately approved deployment.
